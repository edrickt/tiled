A1 · Give a write's expectation one owner, from arm to verdict

Strong in-process

Sources/tiled/FrameWriter.swift · Sources/tiled/DragTracker.swift · Sources/tiled/TilingController.swift · Sources/tiled/TilingSpace.swift

Problem. One write's life is split four ways: FrameWriter arms the expectation and may schedule a check (:89, :94), DragTracker watches the echo and renders the verdict (:197-202, :291-354), TilingController owns the schedulers and the rollback consequence (:423-432, :445-469), and the canvas decides whether a write is verified at all — with the reason for .none living only in a comment (:750-753).

Solution. One owner holds the whole life of an expected write — arm, echo, convergence, consequence — so a call site states only where the window goes and expand/collapse stop being an exception.

  • One owner per write verdict
  • Expand gains a consequence path
  • Bugs concentrate in one module
  • One seam: arm → silence → rollback

A2 · One outcome, announced once

Strong in-process

Sources/tiled/AppDelegate.swift · Sources/tiled/TilingController.swift · Sources/tiled/MenuText.swift

Problem. The controller types an outcome and posts onFeedback (:137-157, :1081-1084), then the delegate's action methods announce success unconditionally — so one action speaks two contradictory sentences, and the tests only pin the delegate's pure helpers.

Solution. One announcement per action, driven by the typed outcome the controller already computes; the delegate adds no success sentence of its own.

  • One announcement per action
  • Pure outcomes reused, not re-guessed
  • Contradictions impossible by shape
  • Delegate becomes a mapping

A3 · Make the death standard's assembly as testable as its decision table

Strong mock

Sources/tiled/LiveWindowGateway.swift · Sources/tiled/TilingController.swift · Sources/tiled/WindowGateway.swift · Tests/tiledTests/FakeWindowGateway.swift

Problem. liveness(of:) gathers fresh app elements, whole window lists, and every listed frame, then feeds a pure table (:212-273 → :754-768) — but no test drives the gathering, and the same call is unbounded work on the main runloop.

Solution. Separate what the app answered (list contents, frame reads, baseline) from what it means, so the death decision is exercised by exact scenarios; make one prune pass ask each app once.

  • Death decision gets a table
  • Ambiguous cases become tests
  • One pass, one app walk
  • Main runloop stops stalling

A4 · One owner for restoring an undo chapter across canvases

Strong in-process

Sources/tiled/TilingController.swift · Sources/tiled/TilingSpace.swift · Sources/tiled/Layout.swift

Problem. Undo is the app's stated safety promise (:786-792) yet its cross-canvas rules are written twice and its least reachable path: the canvas narrates its own restore (:351-358), the controller re-decides everything (:878-892), and the canvas's requester branch is unreachable in production (the controller passes nil, :867).

Solution. Make chapter restoration one named behaviour the controller invokes — it is the only holder of the canvas table — with the canvas supplying its own restore/commit primitives; delete the dead branch.

  • Chapter restore owned once
  • Partial failure reaches the user
  • Dead canvas branch deleted
  • One seam for undo integrity

A5 · One codec for a binding at rest

Strong in-process

Sources/tiled/HotkeyBinding.swift · Sources/tiled/SettingsShortcutsTab.swift

Problem. The same ["modifiers": Int, "keyCode": Int] shape is decoded three times under three rules: HotkeyStore.binding guards modifiers >= 0 — its comment says corrupt data “must not reach UInt32 (a trap)” (:202-205) — while parkedBinding (:541-547) and resetBackupBinding (:774-780) construct UInt32(modifiers) unguarded. Zero mutants target the codec.

Solution. One codec owns the persisted shape for the store, the park, and the reset backup — encode, decode, convention — while the tab keeps only editing behaviour.

  • Corrupt storage cannot trap
  • One validation table
  • Format change is one edit
  • Three readers, one rule

A6 · One refresh pass owns the status item and the menu

Worth exploring in-process

Sources/tiled/AppDelegate.swift · Sources/tiled/MenuModel.swift · Sources/tiled/StatusIcon.swift

Problem. The diff decision has two implementations — refreshPlan (:389-399) and refreshFocusedDisplay (:359-364) — the icon has three writers (:187-195, :347-351, :912-919), and menuSnapshot() claims “one immutable pass” but re-resolves focus three times (:455, :466, :477). One mutant guards all of it.

Solution. One refresh pass computes both snapshots once and owns both diffs; open-menu deferral and focus-driven redraw become decisions of that pass.

  • Staleness reasoned once
  • One writer per snapshot
  • Focus resolved once per pass
  • Deferral rule in one place

A7 · One dependency value and a testable tab lifecycle

Worth exploring in-process

Sources/tiled/SettingsWindowController.swift · Sources/tiled/SettingsGeneralTab.swift · Sources/tiled/SettingsWelcomeTab.swift · Sources/tiled/SettingsShortcutsTab.swift

Problem. The wiring is six closures fanned by didSet (:22-58), tab views rebuilt by hand (:154-179, :200-241), and windowDidResize (:276-280) can never run — nothing assigns the window delegate — so a later rebuild uses the build-time size (SettingsShortcutsTab.swift:495, :513-515). No tests, no mutants.

Solution. Hand the window one dependency value instead of six forwarded closures, and move tab-lifecycle decisions behind named methods a headless test can drive.

  • Resize path lives again
  • One wiring point
  • Tabs drivable headless
  • Stale-size rebuild fixed
